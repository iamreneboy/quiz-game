## Notes

- **`motion` components write animated properties as inline styles, which outrank a Tailwind class regardless of specificity.** P3a shipped a bug where `opacity-45`/`opacity-55` classes sat alongside a `variants` prop animating `opacity` on the same element, and the class silently never won ([ADR-0017](../ADR/0017-answer-selection-is-form-not-hue.md)). Any state that a `motion` component's own `variants`/`animate` touches must be expressed as the variant's target value, not as a co-located class.
- **A component that conditionally mounts based on `useStaging` (or any state derived from `ends_at`) needs `AnimatePresence initial={false}` around that conditional, or its mount-in animation replays on every reload/late-join.** Found three times now — P3a's `QuestionCard` badges and `StageShell` options slot, P3b's `AvatarStack` — because the underlying state is *correct* on a mid-beat mount (spec decision 2) but nothing about that says whether the entrance transition should play. This shape recurs every time a new component mounts conditionally off staging state; check for it by default rather than waiting to find it live. See [ADR-0014](../ADR/0014-beat-position-derived-from-ends-at.md) for the mechanism and why the fix must stay one-shot rather than a blanket store subscription.
- **A cue that can arrive via a reload's *seed* path (not just live cue-bus delivery) must have its side effects applied the instant it is seen, not deferred to a later resolution step keyed to a different cue.** P3b's `final-question` cue sets `useStaging`'s `escalated` flag, but the flag was originally only published from the `phase-track`/`phase-read`/`phase-results` handlers — fine for the live run-up emission (which always arrives immediately before `phase-track` in the same batch), broken for a reload seeded directly into the final round's READ, ANSWER or REVEAL, none of which trigger those handlers. Found live, not by inspection; see [ADR-0021](../ADR/0021-final-question-escalation-fires-on-the-run-up-beat.md). **RESOLVED as a general pattern in P4:** `lib/audio/state.ts`'s `catchUp` flag generalizes this — bed/escalation transitions apply on sight during the seed batch, one-shot stings do not, and a microtask queued on the first post-seed cue ends catch-up exactly at the batch boundary; see [ADR-0024](../ADR/0024-the-first-cue-batch-is-catch-up.md). **CONFIRMED in P5a, live, not just by inspection:** the ceremony (`lib/ceremony/runtime.ts`) subscribes to no cues at all and derives its position purely from the server's `ends_at` via `requestAnimationFrame`, so it never touches the seed-batch/catch-up machinery in the first place — there is no trap to sidestep. A scratch-reverted `advance_phase` test (results phase, `ends_at: null`) and multiple backdated-deadline reloads all landed at the correct elapsed position with zero console errors; see [`P5a-podium-ceremony.md`](P5a-podium-ceremony.md)'s Live-verification findings. Confetti is the one deliberate exception, on purpose: unlike P4's `fanfare` sting, it re-fires once per mount even against an old `ends_at`, because it is a viewer-facing event with no settled state to land in, not game-state audio a seed batch could double-play (see ADR-0029 and the P5a progress doc). **P5b found a fourth guise of the same replay trap, in a component that does *not* mount conditionally — where `AnimatePresence initial={false}` has no purchase at all.** `ResultsTable` and `WinnerCard` are unconditionally rendered from the results phase's first frame (opacity-only staging, ADR-0030), so there is no conditional mount for `AnimatePresence` to guard; but `lib/ceremony/runtime.ts` still initializes `useCeremony`'s store to `NO_CEREMONY` and only publishes the real, possibly-already-settled state a `requestAnimationFrame` tick later — so `steps.board` reads false on first render even when the ceremony ended minutes ago, and without a fix the entrance would still replay on every reload. The fix is a one-shot mount-time derivation (`ResultsView`'s `settled`, read once via a lazy `useState` initializer from the same `ends_at`/`elapsedIn`/`BOARD_AT` the runtime itself uses) rather than a conditional-mount guard. Confirmed live: `results-board`'s `data-entered` attribute read `"true"` immediately on every post-reload check against a long-finished ceremony, never observed transitioning from `"false"`. General rule for any future component staged off `useCeremony` (or any `ends_at`-derived state): if it mounts conditionally, guard with `AnimatePresence initial={false}`; if it doesn't, it needs its own mount-time derivation instead. See ADR-0030.

- **`lib/useHostDriver.ts`'s intermittent `advance_phase` 400, closed by inference rather than repro.** The one-time P4 sighting was never reproduced live, but reading `advance()`'s scheduling `useEffect` against `advance_phase`'s definition (`supabase/migrations/0002_rpcs.sql`) surfaces a real race: the effect depends on the whole `room` object as well as its individual fields, so any unrelated realtime update to `room` while a phase timer is counting down reruns the effect and re-arms a near-zero-delay timer via `msUntil(room.ends_at)`. - **`players.is_playing` has THREE distinct meanings as of M3 P3a, and only `joined_late` separates two of them.** A deliberate MC (a host who chose not to race — never materialised); an unmaterialised late joiner (`joined_late = true`, flipped to playing by `advance_phase` at the next READ with `v_round <= total_rounds`); and — never — a dropped racer, whose `is_playing` is deliberately left alone, because `standings()` filters on that column and demoting them would erase the score PRD §9 says to freeze (ADR-0049). Any code that reads `is_playing` as "is a spectator" must say which of the three it means. Related: `join_room` no longer raises `game already started` at all — a mid-game join is a reclaim or a late join, and only a FINISHED room is refused, now with the specific message `the race has finished` (ADR-0050).
- **`DROP_REPORTS × PRESENCE_REPORT_MS` is a hand-mirror across two files, in the same tradition as `NOMINAL_MS` and `ceremony_ms()`.** `lib/presence.ts` and `supabase/migrations/0009_presence.sql` must move together; `tests/presence.test.ts` and `scripts/smoke.mjs` each pin the product at 60000, so a one-sided change fails a test rather than silently changing PRD §9's grace. The two sides answer the same question differently on purpose: Postgres cannot see a socket, so it counts missed host reports; the client can, so it uses a wall clock. Note the asymmetry before "simplifying" either.
- **A server-side change to a PLAYER row does not reach clients on its own.** There is no server-side realtime and `phase_event` carries no roster (M3 P3a added no key to it), so `absent_reports` and `is_playing` only move on a client at `get_room_state` — on subscribe, or on an explicit refetch. P3a covers the one case that could not wait: `lib/useLateJoinerMaterialize.ts` refetches on each READ, but ONLY for a player who is both `joined_late` and not yet playing, applied through the new narrow `setPlayers` action so it cannot clobber a phase event in flight. **This was found by the e2e test, not by inspection** — the SQL smoke passed the whole time. A future phase needing a roster fact live on every screen needs a broader answer than a per-client refetch; `setPlayers` is the seam.
- **A fresh worktree needs `supabase/.temp/` copied in by hand as well as `.env.local`.** Both are gitignored. Without `.temp/`, `npx supabase db query --linked` answers `Cannot find project ref. Have you run supabase link?` and cannot reach the cloud project at all. Also: do NOT junction `node_modules` from the main checkout into a worktree — Turbopack refuses it outright (`Symlink [project]/node_modules is invalid, it points out of the filesystem root`) and `next dev` will not start. Run `npm install` in the worktree; it takes about 15 seconds with a warm cache.
- **`sweep_host_absence` is the project's only mutating RPC with no host key, and ADR-0051 is the bar for a second.** It is admissible only because it grants the caller nothing: its whole authority is `rooms.host_seen_at`, which only the real host key can refresh, so a client whose host is alive can do nothing at all. Anything that needs the *caller* to be somebody takes a key. The companion rule found while building it: **a `security definer` helper that skips the guards must be revoked from `public`, not just from `anon`/`authenticated`** — Postgres grants EXECUTE to PUBLIC by default, so the narrower revoke left `end_room_now` fully reachable over PostgREST (`has_function_privilege('anon', …)` still answered true). Check with `has_function_privilege`; do not trust the revoke statement.
- **The host's auto-resume ordering is load-bearing: heartbeat FIRST, then read the flag.** `lib/useHostPresenceReporter.ts` calls `report_presence` (which makes `host_absent` false server-side) and only then reads `isHostAbsent` off the store — i.e. off a value that predates that heartbeat. That staleness is deliberate and is the only thing distinguishing a returning host from one who never left; reordering the two calls breaks it silently. Related: `host_absent` is DERIVED on every read and never stored (ADR-0052), which is why `pause_game`, `resume_game`, `skip_question` and `end_game` were not touched and must stay untouched.
- **Any replacement of `get_room_state` or `phase_event` must carry every key the LIVE definition has, not the one a plan quotes.** M3 P3b's plan copied the 0007 body and would have silently dropped `host_seen_at`, which 0009 had added to the same object — and which P3b's own predicate reads. Caught by diffing against the live function before applying. Six migrations in a row have now re-stated these whole bodies; diff before you apply.
- **Nine seconds is three of `presence_report_ms()`** — `host_absence_pause_ms()` joins `DROP_REPORTS × PRESENCE_REPORT_MS`, `NOMINAL_MS` and `ceremony_ms()` as a hand-mirror. If the report cadence moves, this threshold moves with it. Two known limits, both deliberate (ADR-0051): a room whose only remaining surface is a stage view is never swept (a TV holds no player id, so it can never be elected, and the hook is not mounted there), and neither is a room with no clients at all — both sit until the purge takes them.
- **The choreographer has two ways to start a movement sequence, as of M3 P5a.** `beginSequence` compiles buffered drama cues and staggers back-marker first (the passer arrives after the passed); `beginFormationMove` (and its `beginCountdownRollUp` wrapper, used for the lobby → countdown roll-up) takes two anchor sets directly and staggers front row first (a start unspools from the line backwards). A future caller that wants the world to move without a drama cue goes through `beginFormationMove` and must not synthesise a fake cue to reach `beginSequence`. See [ADR-0054](../ADR/0054-the-grid-rolls-up-on-the-servers-countdown.md).
- **`tests/designSystem.test.ts` fails on any raw Tailwind palette class (e.g. `text-slate-400`, `bg-amber-400`) under `components/` or `app/`, as of M3 P5a.** Colour comes from `app/globals.css`'s `@theme` block; a genuinely new colour is a new token there, never a `text-sky-400`. `components/LobbyView.tsx` was the last file this test would have caught — every screen is now on the design system.

## Tech debt / known issues

- **A pre-existing hydration mismatch fires when a HOST reloads mid-game.** `app/room/[code]/page.tsx:79` (`const isHost = typeof window !== 'undefined' && !!loadSession(code)?.hostKey;`) branches on `typeof window` directly in render rather than through `useSyncExternalStore` — the textbook case React's own hydration warning names. The server renders `isHost = false` (so `pb-16` is absent from the wrapper's class list); the client's first render already sees `true` if a host key is stored, and React logs a hydration-mismatch error (it recovers by re-rendering client-side; nothing is visibly broken). A joiner session never triggers it (`isHost` is `false` on both sides). Present since 2026-08-20 (M3 P3b, `0cd6879`); found live during M3 P5a's countdown-reload verification, unrelated to that phase's changes. Not fixed: the shape of the fix is the same `useSyncExternalStore` route `hasSession` on the same file already takes (see the `npm run lint` note above), applied to `isHost`/`hostKey`/`myPlayerId` as well.
