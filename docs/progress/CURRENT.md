## Notes

- **`motion` components write animated properties as inline styles, which outrank a Tailwind class regardless of specificity.** P3a shipped a bug where `opacity-45`/`opacity-55` classes sat alongside a `variants` prop animating `opacity` on the same element, and the class silently never won ([ADR-0017](../ADR/0017-answer-selection-is-form-not-hue.md)). Any state that a `motion` component's own `variants`/`animate` touches must be expressed as the variant's target value, not as a co-located class.
- **A component that conditionally mounts based on `useStaging` (or any state derived from `ends_at`) needs `AnimatePresence initial={false}` around that conditional, or its mount-in animation replays on every reload/late-join.** Found three times now — P3a's `QuestionCard` badges and `StageShell` options slot, P3b's `AvatarStack` — because the underlying state is *correct* on a mid-beat mount (spec decision 2) but nothing about that says whether the entrance transition should play. This shape recurs every time a new component mounts conditionally off staging state; check for it by default rather than waiting to find it live. See [ADR-0014](../ADR/0014-beat-position-derived-from-ends-at.md) for the mechanism and why the fix must stay one-shot rather than a blanket store subscription.
- **A cue that can arrive via a reload's *seed* path (not just live cue-bus delivery) must have its side effects applied the instant it is seen, not deferred to a later resolution step keyed to a different cue.** P3b's `final-question` cue sets `useStaging`'s `escalated` flag, but the flag was originally only published from the `phase-track`/`phase-read`/`phase-results` handlers — fine for the live run-up emission (which always arrives immediately before `phase-track` in the same batch), broken for a reload seeded directly into the final round's READ, ANSWER or REVEAL, none of which trigger those handlers. Found live, not by inspection; see [ADR-0021](../ADR/0021-final-question-escalation-fires-on-the-run-up-beat.md). **RESOLVED as a general pattern in P4:** `lib/audio/state.ts`'s `catchUp` flag generalizes this — bed/escalation transitions apply on sight during the seed batch, one-shot stings do not, and a microtask queued on the first post-seed cue ends catch-up exactly at the batch boundary; see [ADR-0024](../ADR/0024-the-first-cue-batch-is-catch-up.md). **CONFIRMED in P5a, live, not just by inspection:** the ceremony (`lib/ceremony/runtime.ts`) subscribes to no cues at all and derives its position purely from the server's `ends_at` via `requestAnimationFrame`, so it never touches the seed-batch/catch-up machinery in the first place — there is no trap to sidestep. A scratch-reverted `advance_phase` test (results phase, `ends_at: null`) and multiple backdated-deadline reloads all landed at the correct elapsed position with zero console errors; see [`P5a-podium-ceremony.md`](P5a-podium-ceremony.md)'s Live-verification findings. Confetti is the one deliberate exception, on purpose: unlike P4's `fanfare` sting, it re-fires once per mount even against an old `ends_at`, because it is a viewer-facing event with no settled state to land in, not game-state audio a seed batch could double-play (see ADR-0029 and the P5a progress doc). **P5b found a fourth guise of the same replay trap, in a component that does *not* mount conditionally — where `AnimatePresence initial={false}` has no purchase at all.** `ResultsTable` and `WinnerCard` are unconditionally rendered from the results phase's first frame (opacity-only staging, ADR-0030), so there is no conditional mount for `AnimatePresence` to guard; but `lib/ceremony/runtime.ts` still initializes `useCeremony`'s store to `NO_CEREMONY` and only publishes the real, possibly-already-settled state a `requestAnimationFrame` tick later — so `steps.board` reads false on first render even when the ceremony ended minutes ago, and without a fix the entrance would still replay on every reload. The fix is a one-shot mount-time derivation (`ResultsView`'s `settled`, read once via a lazy `useState` initializer from the same `ends_at`/`elapsedIn`/`BOARD_AT` the runtime itself uses) rather than a conditional-mount guard. Confirmed live: `results-board`'s `data-entered` attribute read `"true"` immediately on every post-reload check against a long-finished ceremony, never observed transitioning from `"false"`. General rule for any future component staged off `useCeremony` (or any `ends_at`-derived state): if it mounts conditionally, guard with `AnimatePresence initial={false}`; if it doesn't, it needs its own mount-time derivation instead. See ADR-0030.
- **Local Supabase runs on shifted ports and the shift is not in git.** Windows/Hyper-V has reserved TCP 54024–54423, which covers every default Supabase port, so `.env.local` (gitignored) points at 553xx instead while `supabase/config.toml` was deliberately left at defaults. The running stack matches `.env.local`, so it works as-is — but **do not run `supabase stop` or `supabase start`**, because a restart will bind the reserved defaults, fail, and lose the working stack. **This also applies to every fresh git worktree, not just a fresh machine**: `.env.local` is gitignored, so `git worktree add` does not copy it — it must be copied by hand from the main checkout and its port corrected before `npm run dev` can reach the database (found while setting up P3a's worktree; the main checkout's own `.env.local` had then been found pointing at the unshifted default port — resolved 2026-08-25: the stack serves on 55321 and the main `.env.local` matches it. Note that `supabase status` prints config.toml's defaults (54321), not the live bindings — don't trust it for ports on this machine).

- **Inside `[data-surface="stage"]`, Tailwind spacing and type utilities do not mean what they mean anywhere else in the app.** P6b rescales the whole stage surface by redefining the *existing* theme variables in that scope in `app/globals.css` — `--spacing`, `--text-hero`, `--text-display`, `--container-4xl`, `--container-6xl`, all in `cqi` against a `container-type: size` root. Every Tailwind v4 utility resolves through a theme var (`.p-8` → `calc(var(--spacing) * 8)`, `.max-w-6xl` → `var(--container-6xl)`), which is exactly why `RevealPanel`, `WinnerCard`, `ResultsTable` and `AvatarStack` rescale for a television with **no edits to any of them** — and exactly why editing one of those shared components means checking both surfaces. Deliberate action at a distance; the trade and the rejected alternative (a parallel `--stage-*` namespace plus a stage-only copy of every shared component) are in [ADR-0035](../ADR/0035-the-stage-rescales-by-scoped-token-override.md), and `globals.css` says so at the block. Related: `--horizon-fraction` is a hand-mirror of `HORIZON_FRACTION` (`tests/tokens.test.ts` fails if they drift) so DOM chrome can be pinned to the world's ground line.

- **`total_rounds` is mutable mid-game, as of M3 P0.** `skip_question` decrements it and shortens the track (ADR-0038); the phase event carries the live value on every event, not just at room creation (ADR-0037). Any future consumer that snapshots `total_rounds` once (at room creation, or on first sight) rather than reading it off the live phase event or `useGameStore` is wrong — `lib/store.ts` and `lib/presentation/deriveCues.ts` both already treat it as live. **A change in it is also a beat change *and* possibly an escalation trigger:** `deriveCues` puts `total_rounds` in its `phaseChanged` comparison (a skip during READ changes neither phase nor round), and synthesizes `final-question` when the change lands on `round === total_rounds`, because the run-up TRACK that normally escalates is already behind the shortened track — closed 2026-08-29, outside any phase; see ADR-0038's amended consequence for why it cannot double-announce.
- **`lib/useHostDriver.ts`'s intermittent `advance_phase` 400, closed by inference rather than repro.** The one-time P4 sighting was never reproduced live, but reading `advance()`'s scheduling `useEffect` against `advance_phase`'s definition (`supabase/migrations/0002_rpcs.sql`) surfaces a real race: the effect depends on the whole `room` object as well as its individual fields, so any unrelated realtime update to `room` while a phase timer is counting down reruns the effect and re-arms a near-zero-delay timer via `msUntil(room.ends_at)`. If the original `advance()` call is still awaiting its RPC round-trip when that happens, the re-armed timer fires a second `advance()` immediately. The DB function re-reads the room fresh under `for update`, so the second call sees whatever the first just committed — usually harmless (the `case` still matches), but on the final round's `track → results` transition the room lands on `status = 'finished'`, which `advance_phase` rejects outright (`raise exception 'game not started'`), and PostgREST reports that as 400. Fixed with an `advancing` ref in `useHostDriver` that makes a call arriving while one is already in flight a no-op. No regression test: this repo has no React-hook test infrastructure (no `@testing-library/react`/jsdom, `vitest.config.ts` only includes `tests/**/*.test.ts`), and building that infra just to pin a timing race was judged out of proportion to the fix. Verified with `npx tsc --noEmit` and `npm run lint` only — if the 400 recurs, that's the signal the hypothesis was wrong, not just unlucky timing.
- **`total_rounds` is now mutable before the game starts too, as of M3 P1.** `add_custom_question` and `remove_question` change it while `status = 'lobby'`, same field, different trigger from the mid-game mutability M3 P0 already recorded above. No realtime event carries it at that point — `start_game`'s phase event does (ADR-0037), not a lobby-phase broadcast. A client resident in the lobby therefore holds a stale `total_rounds` by design; it self-corrects the moment `start_game` fires the first phase event at the countdown.
- **`questions` is no longer purely a bank table, as of M3 P1.** A row with a non-null `room_id` belongs to exactly one room — it is a custom question, not bank inventory (ADR-0039). Every query that draws from the bank must say `and room_id is null`; four do today, all in `supabase/migrations/0006_the_draw.sql` (`create_room`'s availability count, `create_room`'s draw, the reserve draw, `swap_question`'s replacement draw). A fifth that forgets would leak one room's private question into another room's game.

- **`current_round` can exceed `total_rounds`, as of M3 P2a.** The tiebreak is a real round at `total_rounds + 1`, not a phase (ADR-0043) — `question_public`, `build_reveal`, `submit_answer`, the timer ring and `useHostDriver` all work on it unchanged, which is the whole point. Two obligations follow. Anything that renders `round`/`total_rounds` must special-case it or print nonsense ("Q13/12"); `components/QuestionCard.tsx` does, off `useStaging`'s `suddenDeath` flag. And anything that computes a scoring bound must go through `scoring_round(room_id, round)`, which clamps to `total_rounds` — that single clamp is what keeps a tiebreak answer from becoming a correct answer, and a future caller that forgets it will silently count the tiebreak. Four callers exist today, all in `0007_the_tiebreak.sql`.
- **The ceremony is 12400ms, flat, whether or not a photo finish is staged** (ADR-0044). `lib/ceremony/beats.ts`'s `CEREMONY_MS` is the hand-maintained mirror of migration 0007's `ceremony_ms()`, in the same tradition as `NOMINAL_MS`; `PHOTO_MS` (3400) shifts the podium's beats when a prelude is staged but never the total, so the server never has to detect a tie. A change to either number must move both, and `tests/ceremonyBeats.test.ts` pins `PHOTO_MS + BOARD_AT < CEREMONY_MS` so a later change fails a test rather than truncating the board's entrance.
- **The celebration hierarchy is six rungs, and M3's one allowed addition is spent.** `suddenDeath` sits between `finalQuestion` and `victory` (roadmap decision 6). The photo finish deliberately gets no rung. Nothing else in M3 may claim one.
- **A reload that lands exactly on a phase boundary can resubscribe after the broadcast and sit on stale staging until the next phase event.** Found in M3 P2a while stabilising the sudden-death e2e test, reproduced twice: a reload straddling READ→ANSWER left `steps.optionsMode` at `dim` for a whole 20s ANSWER phase, so the grid never went live. **Not tiebreak-specific — any phase boundary can do it — and not fixed.** The e2e test sidesteps it by reloading well inside the READ. The shape of a real fix is `lib/useRoomChannel.ts` re-fetching `get_room_state` once after the channel reports `SUBSCRIBED`, since the phase event it missed is exactly what that call would replace.

- **`npx supabase db query` cannot apply a migration to this machine's local stack — use `docker exec … psql`.** Found in M3 P2b. With no flags the CLI dials `config.toml`'s default `54322` and gets `ECONNREFUSED` (the stack is on the shifted `553xx` ports); with an explicit `--db-url` at the real port it fails on TLS, and with `sslmode=disable` it fails on `cannot insert multiple commands into a prepared statement`, because it sends the whole file as one prepared statement. No multi-statement migration in this repo can survive that. What works: `docker exec -i supabase_db_quiz-game psql -U postgres -d postgres -v ON_ERROR_STOP=1 < supabase/migrations/<file>.sql`. **Then reload PostgREST's cache** — `docker exec supabase_db_quiz-game psql -U postgres -d postgres -c "notify pgrst, 'reload schema';"` — or every call to a brand-new RPC answers `Could not find the function … in the schema cache`, which looks exactly like a migration that did not apply. The `--linked` cloud path is unaffected and still works as CURRENT.md describes.
- **`speed_points` is a SUM over a racer's correct answers, not a per-question best** (`supabase/migrations/0002_rpcs.sql:45`). Obvious in the code, easy to get wrong when reasoning about outcomes: it means the racer with the most correct answers almost always has the most speed points too, whatever anyone's reaction time. M3 P2b's plan built a whole smoke fixture on the opposite assumption and it could not pass. Any future scenario that needs Fastest Gun to differ from Big Brain must make the high scorer answer everything LATE.
- **The question bank holds exactly two rows per (category, tier) — 48 in total — and `correct_index` is spread across all four options.** Two consequences that have each already cost a debugging pass. A room drawing from one category exhausts that category in two races, so `rematch` refuses the third (correctly — ADR-0046); a fixture that needs more must select more categories. And **no browser test may assume the first option is correct**: it is right about 29% of the time, which is exactly flaky enough to look like a timing bug. `e2e/aftermath.spec.ts` handles it by fielding four racers who cover all four options, which makes exactly one answer correct and every award single-winner. M3 P4 (the bank) is what relieves the first half of this.
- **`current_round` can exceed `total_rounds`, and a room can now also move BACKWARDS, as of M3 P2b.** A rematch returns the room to `lobby` from `results` (ADR-0046), which is the first backwards transition in the game's history. Anything holding forward-only state must be told: today that is the camera, the audio bed and `deriveCues`' standings baseline, and the telling is the `game-reset` cue (ADR-0047), never a per-consumer `phase === 'lobby'` check. A new consumer that accumulates across a race — a counter, a baseline, a parked shot — needs a `game-reset` arm, and the cue bus is where it goes.
- **`total_rounds` is mutable BETWEEN games too, as of M3 P2b** — the third trigger, after M3 P0's mid-game skip and M3 P1's pre-game add/remove. `rematch` rewrites it from the histogram of the previous draw. The rule is unchanged and now has three witnesses: read it live off the phase event or `useGameStore`, never snapshot it.
- **`rooms.used_question_ids` grows without bound.** Roughly one uuid per round per rematch, appended forever, and nothing prunes it. It is the natural thing for M3 P3's 24-hour room purge to reclaim — the array dies with the row.
