## Notes

- **`motion` components write animated properties as inline styles, which outrank a Tailwind class regardless of specificity.** P3a shipped a bug where `opacity-45`/`opacity-55` classes sat alongside a `variants` prop animating `opacity` on the same element, and the class silently never won ([ADR-0017](../ADR/0017-answer-selection-is-form-not-hue.md)). Any state that a `motion` component's own `variants`/`animate` touches must be expressed as the variant's target value, not as a co-located class.
- **A component that conditionally mounts based on `useStaging` (or any state derived from `ends_at`) needs `AnimatePresence initial={false}` around that conditional, or its mount-in animation replays on every reload/late-join.** Found three times now — P3a's `QuestionCard` badges and `StageShell` options slot, P3b's `AvatarStack` — because the underlying state is *correct* on a mid-beat mount (spec decision 2) but nothing about that says whether the entrance transition should play. This shape recurs every time a new component mounts conditionally off staging state; check for it by default rather than waiting to find it live. See [ADR-0014](../ADR/0014-beat-position-derived-from-ends-at.md) for the mechanism and why the fix must stay one-shot rather than a blanket store subscription.
- **A cue that can arrive via a reload's *seed* path (not just live cue-bus delivery) must have its side effects applied the instant it is seen, not deferred to a later resolution step keyed to a different cue.** P3b's `final-question` cue sets `useStaging`'s `escalated` flag, but the flag was originally only published from the `phase-track`/`phase-read`/`phase-results` handlers — fine for the live run-up emission (which always arrives immediately before `phase-track` in the same batch), broken for a reload seeded directly into the final round's READ, ANSWER or REVEAL, none of which trigger those handlers. Found live, not by inspection; see [ADR-0021](../ADR/0021-final-question-escalation-fires-on-the-run-up-beat.md). **RESOLVED as a general pattern in P4:** `lib/audio/state.ts`'s `catchUp` flag generalizes this — bed/escalation transitions apply on sight during the seed batch, one-shot stings do not, and a microtask queued on the first post-seed cue ends catch-up exactly at the batch boundary; see [ADR-0024](../ADR/0024-the-first-cue-batch-is-catch-up.md). **CONFIRMED in P5a, live, not just by inspection:** the ceremony (`lib/ceremony/runtime.ts`) subscribes to no cues at all and derives its position purely from the server's `ends_at` via `requestAnimationFrame`, so it never touches the seed-batch/catch-up machinery in the first place — there is no trap to sidestep. A scratch-reverted `advance_phase` test (results phase, `ends_at: null`) and multiple backdated-deadline reloads all landed at the correct elapsed position with zero console errors; see [`P5a-podium-ceremony.md`](P5a-podium-ceremony.md)'s Live-verification findings. Confetti is the one deliberate exception, on purpose: unlike P4's `fanfare` sting, it re-fires once per mount even against an old `ends_at`, because it is a viewer-facing event with no settled state to land in, not game-state audio a seed batch could double-play (see ADR-0029 and the P5a progress doc). **P5b found a fourth guise of the same replay trap, in a component that does *not* mount conditionally — where `AnimatePresence initial={false}` has no purchase at all.** `ResultsTable` and `WinnerCard` are unconditionally rendered from the results phase's first frame (opacity-only staging, ADR-0030), so there is no conditional mount for `AnimatePresence` to guard; but `lib/ceremony/runtime.ts` still initializes `useCeremony`'s store to `NO_CEREMONY` and only publishes the real, possibly-already-settled state a `requestAnimationFrame` tick later — so `steps.board` reads false on first render even when the ceremony ended minutes ago, and without a fix the entrance would still replay on every reload. The fix is a one-shot mount-time derivation (`ResultsView`'s `settled`, read once via a lazy `useState` initializer from the same `ends_at`/`elapsedIn`/`BOARD_AT` the runtime itself uses) rather than a conditional-mount guard. Confirmed live: `results-board`'s `data-entered` attribute read `"true"` immediately on every post-reload check against a long-finished ceremony, never observed transitioning from `"false"`. General rule for any future component staged off `useCeremony` (or any `ends_at`-derived state): if it mounts conditionally, guard with `AnimatePresence initial={false}`; if it doesn't, it needs its own mount-time derivation instead. See ADR-0030.
- **Local Supabase runs on shifted ports and the shift is not in git.** Windows/Hyper-V has reserved TCP 54024–54423, which covers every default Supabase port, so `.env.local` (gitignored) points at 553xx instead while `supabase/config.toml` was deliberately left at defaults. The running stack matches `.env.local`, so it works as-is — but **do not run `supabase stop` or `supabase start`**, because a restart will bind the reserved defaults, fail, and lose the working stack. **This also applies to every fresh git worktree, not just a fresh machine**: `.env.local` is gitignored, so `git worktree add` does not copy it — it must be copied by hand from the main checkout and its port corrected before `npm run dev` can reach the database (found while setting up P3a's worktree; the main checkout's own `.env.local` was itself found pointing at the unshifted default port — worth checking whether that's stale or the stack was since restarted).
- **Headless Chromium cannot be used to measure frame budget.** It falls back to SwiftShader, idles around 16fps with `dropped 75/76`, and pins the VFX budget at `minimal` before a test starts. CDP CPU throttling is also the wrong instrument — the render loop is GPU-bound. Headed browser plus a synthetic main-thread block is the combination that works; that is how P2's exit criterion 5 was verified. P3a and P3b's live verification (reload timing, tension-ramp sampling, animation-replay detection) used a headed browser throughout for the same reason.
- **`npm run lint` is now clean — there is no longer a "one known pre-existing error" to discount.** The `react-hooks/set-state-in-effect` error that sat in `app/room/[code]/page.tsx` from before M2 (`setHasSession` called synchronously inside a `useEffect`) was fixed on 2026-08-24, outside any phase, by the route the debt entry itself had already identified as the React-correct one: `useSyncExternalStore` with a `null` server snapshot and `() => !!loadSession(code)` as the client snapshot. `lib/session.ts` gained a `subscribeSession` listener set, notified from `saveSession` — the app's only writer (`JoinGate`, `app/host/new`) — which is what makes the session a real external store rather than something copied into React state. `handleJoined`'s `setHasSession(true)` was dropped as redundant: `JoinGate` calls `saveSession` *before* `onJoined`, so the notification has already landed. The `null`-means-not-known-yet render path is unchanged, so hydration still matches. Verified with `npx tsc --noEmit` (silent), `npm run lint` (zero problems), `npm test` (429 passed), `npm run build`, and `npm run test:e2e -- --workers=2` (21 passed, join flow included). **Any lint error from here on is a real one — do not discount it.**
- **`npm run test:e2e` at this machine's default worker count (unset outside CI, so Playwright picks one per CPU core) is flaky under load**, timing out on unrelated, pre-existing lobby/countdown assertions in a different subset of tests each run. Found in P3b: `--workers=2` passed cleanly and reproducibly every time across several runs where the default count flaked on 2-4 tests. Not fixed (`playwright.config.ts` is untouched); if it recurs, that file's `workers` setting is the place to look, not the tests themselves.

## Tech debt / known issues

- **Tied players share a compressed stack rather than offsetting in x** (P2). All-tied cases — the start line, the round-1 TRACK beat — are a tight heap of overlapping rigs. The stack is capped at `MAX_STACK_RISE` so everyone stays on canvas, which was the point, but the readable answer is two rigs per row offset in x. **Blocked on a contract change:** that requires `row` to stop meaning "unique rank within the segment", which `flairFor`'s edge-holder rule reads.
- **`TRACK_MARGIN` is the last P1 constant still sized against the deleted marker puck** (P2). The lobby grid lives entirely in the 260-unit run-off, and the run-off was sized for a 52-unit puck, not a 90-unit rig — so once `GRID_EDGE_MARGIN` reserved room to draw the rearmost rig whole, column spacing compressed from 73 to 51 units and adjacent same-row rigs now overlap by about a third of their rim. This is the same root cause as P2's Critical (a P1 constant that stopped matching what gets drawn), and it was left alone deliberately: `TRACK_MARGIN` sets the world's `minX`/`maxX`, so changing it moves the camera bounds and re-tests framing. **Fix:** widen the run-off and re-verify the camera, as its own piece of work rather than a fix tacked onto a phase close.
- **`MAX_STACK_RISE` is derived at 16:9 and applied at every aspect ratio** (P2). A deep tie puts the top rig's head at screen y +23.5 on 1920×1080 but −227.8 on 2560×1080 and −314.3 on 3440×1440. Not a regression of P2's Critical — the y-aware `offscreenPlayerIds` names those players and the readout marks them off screen — but ultrawide viewers lose the top of a deep stack to the readout instead of the canvas. **Blocked:** the honest fix needs the viewport inside `markerAnchors`, which is pure and viewport-free by contract; letting the camera widen instead is the answer the Critical's fix explicitly rejected. **P6a's stage view is now live and is exactly the surface that cares** — a landscape TV at a non-16:9 aspect is its normal deployment — so this is P6b's scope.
- **The readout's off-screen marker carries no direction** (P2). It used to render a fixed `◀`, which was already wrong for players off the right and became wrong for players off the top once the check went y-aware, so it was reduced to a non-directional marker. **Fix:** have `offscreenPlayerIds` return a direction per player and render it — deferred because it changes a pure module's return type, `useWorldView`'s state shape, and every caller and test.
- **`lib/useHostDriver.ts`'s `advance_phase` RPC call intermittently 400s.** Seen once during P4 verification (a track-beat transition in an otherwise-normal game), not seen again across roughly a dozen other headed playthroughs including longer/more complex ones run immediately after. Game state still advanced correctly the one time it fired — a retried or duplicate call being rejected by a server-side guard is the likely shape, but not confirmed. `lib/useHostDriver.ts` is untouched by P4; not investigated further as out of scope. Worth a proper look if it recurs with any regularity.
- **The winner's podium rig is clipped by the top of the canvas once the results band retreats to 50vh** (P5a). `lib/world/framing.ts`'s podium camera shot scales purely off viewport *width* (`worldScale = viewport.width / camera.span`), by design — it deliberately does not read anchors or reason about vertical space at all. That is fine at the full-height (100vh) canvas shown before the board retreats, but once `steps.board` flips and the canvas shrinks to 50vh, the same width-driven scale is now applied against half the vertical pixels, and the math pushes the winner's rig top to roughly screen y ≈ −80 on a 1280×360 canvas. Same class of issue as the `MAX_STACK_RISE` entry above (a shot sized without accounting for how tall the screen space actually is at the moment it renders). **Fix:** scope as its own piece of work; the honest fix is either new vertical-headroom reasoning in the podium framing math or changing when the retreat happens relative to the shot, both real design decisions, not a one-line clamp. **Re-checked in P5b, live, with the real board in place:** the clipping still reproduces unchanged — every settled screenshot taken during P5b's verification shows the winner's rig cropped at the top of the 50vh canvas, same as P5a's original measurement. P5b judged the retreat *more* clearly worth its price now than before, not less: in P5a the retreat was reserving space for a board that didn't exist yet, whereas it now makes room for a real, complete, accessible results board (confirmed working end to end; see [`P5b-results-board.md`](P5b-results-board.md)). The clipping remains a real, unaddressed visual defect and is still worth its own scoped fix, but nothing found during P5b suggests reconsidering the retreat itself. **Re-confirmed again in P6a on the stage view**, which shares the same band and the same podium shot — every settled stage screenshot shows the same crop. Spec §12 named it out of P6a's scope explicitly; **this is P6b's scope.**
- **A late-reloading or late-joining viewer can see confetti burst at full density under a reduced or budget-degraded profile** (P5a). `lib/world/runtime.ts`'s `budget` always starts at `initialBudgetState` (`full`), regardless of `profile`, and only converges to the correct level via `stepBudget` after the runtime's own first ~500ms tick. Every other VFX consumer is a continuous emitter and self-corrects invisibly inside that window; confetti is a one-shot burst, so if a client mounts (via join or reload) directly into an already-elapsed ceremony past `CONFETTI_AT`, the burst can fire at whatever density `budget` happened to start at, with no chance to self-correct afterward. Reproduced live, twice, while trying to verify the `lean` confetti density. Pre-existing `vfxBudget` (P2) characteristic, not introduced by P5a — confetti is just the first one-shot consumer sensitive to it. **Fix:** seed `budget` from `profile` at `createWorldRuntime` construction instead of always starting `full`; small and plausibly correct, but out of scope for the task that found it.
