## Scope (from the spec)

P5a replaces the results screen's terminal table-swap with a produced podium ceremony on the Pixi canvas: three blocks rising bronze → silver → gold, a spotlight finding the winner, and budget-governed confetti — then a band retreat that hands the lower half of the screen to P5b's (not-yet-built) results board. Carries migration 0004: a deadline for the results phase, and two additive `standings()` stat fields (`answered`, `avg_answer_ms`) P5b will consume.

## Deviations from the plan (as shipped)

Before writing any code, the plan was reviewed critically against the actual codebase (not just read) — cross-checking every cited file:line, every existing test the plan's new tests would run alongside, and the two claims most load-bearing to the whole phase. That review surfaced one significant gap and two small ones; all three were fixed before or during implementation rather than shipped as written.

1. **The block-rise animation mechanism did not exist — found before writing code, fixed with the user's sign-off.** Both the spec (§6: *"the existing movement grammar animates the lift... `avatarStates` already interpolates toward anchors"*) and the plan (Tasks 3 and 8) assumed that changing a `MarkerAnchor`'s position causes it to glide smoothly, the way a TRACK-beat overtake does. Reading `lib/world/choreographer.ts` and `lib/world/movement.ts` directly disproved this: interpolation only happens inside an active choreographer `Sequence`, which is only ever constructed by `beginSequence`, itself only ever invoked on a `phase-track` cue. The podium's bronze/silver/gold thresholds are elapsed-time boundaries inside the results phase, not cues, and nothing in the plan wired a sequence to them — so as specified, every block and its rig would have **snapped** into place in a single frame rather than rising. This was raised with the user directly (`AskUserQuestion`) with three options — accept a stepped "pop" reveal, add continuous eased progress, or pause for a plan revision. The user chose continuous eased progress. The fix stays inside the pure layer and touches no choreography code at all: `CeremonySteps.rise` (Task 2) became a **linear** 0..1 progress per place instead of a discrete `risen: 0|1|2|3` flag, and `lib/world/podium.ts` (Task 3) applies `cubicBezierEase(EASE.settle, …)` — the same curve `lib/world/movement.ts` gives a travelling avatar — when it turns that progress into a world-space `y`. Because the anchor is recomputed fresh every tick from real elapsed time, it already moves smoothly frame to frame; `avatarStates`' "no smoothing" behavior, which looked like the bug, is exactly what renders it correctly once the anchor itself is continuous. `PodiumBlock.riseProgress` (not `risen: boolean`) carries the identical eased value into the renderer, so the block and the rig standing on it read one shared number and cannot desync. Full reasoning in [ADR-0026](../ADR/0026-the-podium-is-a-fourth-anchor-layout.md). This touched Tasks 2, 3 and 8's interfaces and their test suites more than the plan anticipated — a real, contained scope increase the user explicitly approved, not a silent one.
2. **Task 9's confetti mount order was backwards relative to its own stated intent — found during review, fixed before commit.** The plan's Task 9 Step 2 said to mount confetti "**above** the grade so pieces are not washed out by it," then gave an insertion point (`this.root.addChild(this.confetti.container)`, immediately *before* `this.root.addChild(this.grade.graphic)`) that puts it *behind* grade in Pixi's paint order — the opposite of the stated goal. Since Task 5 deliberately holds `escalation` at 1 through the whole ceremony (see item 3 below), `Grade` renders at ~0.31 peak alpha neon-magenta at that point, which would have visibly tinted the burst. Corrected to add confetti's container *after* grade's; confirmed live (Verification) that a full-density burst renders in clean, saturated colour against a visibly graded background in the same frame.
3. **Task 5's own change broke a pre-existing test — found before running it, fixed in the same commit.** `tests/director.test.ts`'s `'ignored cues'` test hardcoded `{ type: 'phase-results', tier: 'routine' }` into an array asserted via `.toBe(base)` — strict referential equality, i.e. "this cue is a no-op." Task 5 adds a real `case 'phase-results':` branch to `reduceCue`, which returns a new object for that cue, so the assertion could not survive as written. The plan's Task 5 never mentioned this existing test. Removed the one entry rather than leave a known-failing assertion in the suite; the rest of that test's array (including the unrelated `podium` cue, still correctly ignored) is untouched.

## Deviations from the spec the plan itself already made (executed as planned, recorded here per Task 10's own instruction)

- **`podiumX` is the finish line itself, not `finish + TRACK_MARGIN * 0.45`.** `TRACK_MARGIN` is only 260 world units and `camera.ts`'s minimum span is 800, so `clampCamera` pins the camera's right edge at `metrics.maxX` — the spec's value would have framed the podium off the right of the canvas. Same root cause as the `TRACK_MARGIN` tech debt already in `CURRENT.md`. This was the plan's own call, made explicitly in Task 3 and its Self-Review section, and implemented as written; recorded here again per [ADR-0026](../ADR/0026-the-podium-is-a-fourth-anchor-layout.md).
- **`podiumAnchors` preserves `row` rather than forcing it to `0`.** `flairFor` computes `edgeHolder = contested && row === 0` (`lib/world/flair.ts:73`); two podium players tied on `correct` share a segment with rows 0 and 1, and forcing `row: 0` on both would light the turbo flame on both instead of the one actually holding the edge. Tested directly (`tests/podium.test.ts`, "preserves row") and exercised live against WASHV's real tie between `sheila` and `mocha` (both 7 correct, differentiated by speed points) — silver and bronze rendered as two distinct blocks with no double-flame.

## Deviations found during implementation (not anticipated by the plan)

- **The winner's rig head is clipped by the top of the canvas once the band retreats to 50vh — confirmed live, not hypothetical.** Task 10 Step 5 asked whether this happens at non-16:9 aspect ratios; it turns out to happen at the *default* 16:9 viewport too, because the podium camera's scale is driven by viewport **width** (`worldScale = viewport.width / camera.span`) while the results canvas is deliberately shrunk to 50% of viewport **height** post-`board` (Task 7). At a 1280×360 canvas (50vh of a 720-tall viewport) with the podium's ~922-world-unit span, the winner's rig top computes to screen y ≈ −80 — above the frame — and every live screenshot taken after the board retreated shows exactly this: the winner's rig is visibly cropped at the top edge. Before the retreat (canvas at 100vh) the same rig sits comfortably in frame. This is the same class of issue as the existing `MAX_STACK_RISE` debt (a world-unit constant sized without accounting for how tall the *available* screen space actually is at the moment it matters) — **added to `CURRENT.md`'s tech debt** rather than fixed here, since a fix means either reserving headroom in `PODIUM_SPAN`'s vertical framing (which this camera mode does not currently reason about at all — it is width/span only, by design, per `framing.ts`'s own doc comment) or changing when the band retreats relative to the podium shot, both real design decisions outside this task's scope.
- **A late-reloading or late-joining viewer can see a full-density confetti burst under a reduced or degraded profile, if their client mounts directly into an already-elapsed ceremony past `CONFETTI_AT`.** Found while trying to live-verify the `lean`/`minimal` confetti density (see Live-verification findings). Root cause: `lib/world/runtime.ts`'s `budget` always starts at `initialBudgetState` (`full`) regardless of `profile`, and only converges to the correct level via `stepBudget` after the runtime's own first ~500ms tick. For every other VFX element this is invisible — continuous emitters self-correct within that same 500ms. Confetti is the first **one-shot** consumer of the budget, so if its burst happens to fire before that first evaluation (which it will, if the ceremony's own elapsed-time clock is already past `CONFETTI_AT` at mount — an entirely normal thing for a reload or late join to hit), the whole multi-second burst plays at whatever density `budget` happened to start at, with no self-correction possible after the fact. This is a pre-existing characteristic of the `vfxBudget` system from P2 (`lib/world/vfxBudget.ts`'s `stepBudget`), not something this phase introduced — P5a's confetti is simply the first thing sensitive enough to a timing gap that every other VFX consumer already has and tolerates. **Added to `CURRENT.md`'s tech debt** rather than patched here: the fix (seed `budget` from `profile` at construction instead of always starting `full`) is small and plausibly correct, but it is a `runtime.ts`/`vfxBudget.ts` change outside a task titled "confetti," and does not belong going in unasked this late in the phase.

## Live-verification findings

Every task's Pixi/DOM-visible behavior was checked in a **headed** `playwright-cli` session against the real local Supabase stack — never against headless Chromium, which `CURRENT.md` already documents as unusable for anything budget- or frame-timing-sensitive (SwiftShader fallback, ~16fps, pinned at `minimal` before a check can even begin). The perf overlay (`?perf=1`) confirmed genuine GPU-backed rendering throughout this session: **143–145fps, 0/120 dropped frames** at rest.

Rather than play fresh games for every check, the real finished room `WASHV` (4 players, real differentiated standings: `rene` 9 correct/1st, `sheila` 7 correct/1083 speed/2nd, `mocha` 7 correct/637 speed/3rd — a real tie on `correct` broken by speed, `Toby` 6 correct/4th) had its `phase_ends_at` re-armed via direct `docker exec psql` between checks. This is the same "never committed, this project's convention for manual checks" pattern P4's progress doc records, extended here to reuse one real room's data across many checks instead of re-playing a game each time.

**Not caught live: the `lean` (density 0.5) confetti frame specifically.** Every attempt at a precisely-timed mid-burst screenshot at `lean` landed either before or after the piece lifetime (~3.2s), because `playwright-cli`'s per-command latency (observed 1–20+ seconds depending on the command and prior state) made hitting an exact live window unreliable, and attempts to force a downgrade via a sustained main-thread block (the P2 exit-criterion-5 technique) either had already recovered by the time a screenshot completed, or — per the P2 progress doc's own record of that same technique — tend to shed straight to `minimal` rather than stopping at `lean`. `full` (density 1) and `minimal` (density 0, via the reduced-motion pin) were both directly confirmed; `lean` shares the exact same `burst()` code path as `full`, just a smaller `count` and no `spin`, and its allowance value (`0.5`) is unit-tested (`tests/vfxBudget.test.ts`). Recorded as an honest gap rather than claimed.
